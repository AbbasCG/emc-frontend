## 0. المبدأ الحاكم

> **الوضوح قبل الإبهار. كل عنصر على الشاشة يجب أن «يكسب» مكانه — وإلا يُحذف.**

خمسة مبادئ تقود كل قرار في هذه الخطة:

1. **تقليل الحِمل الإدراكي** — أقلّ عناصر، تباين بصري أوضح، تدرّج هرمي واحد للعين تتبعه.
2. **الكشف التدريجي (Progressive Disclosure)** — أظهِر الأساسي الآن، وأخفِ المتقدّم خلف «المزيد».
3. **حركة هادئة وهادفة** — الحركة تُرشِد لا تُبهر؛ افتراضٌ ساكن، واستثناءٌ متحرّك.
4. **أقصر مسار للإنجاز** — كل خطوة تُحذَف أو تُدمَج ما لم تكن ضرورية؛ قيمٌ افتراضية ذكية بدل أسئلة.
5. **اتّساق صارم** — مكوّن واحد لكل غرض، token واحد لكل لون، نمط واحد لكل تفاعل.

| 🪜 **خطوات كثيرة** | تدفّقات طويلة: التسجيل (`Register.tsx` ~19KB)، معالج النماذج (`emc-form-wizard` ~17KB)، طلب ورشة (`SubmitWorkshop` ~49KB)، التطوّع (`VolunteerApply` ~19KB) | تقرير 02 |

## 2. سياسة الحركة والضجيج البصري (علاج «الرسومات تُشتِّت») 🎬

### 2.1 قاعدة الحركة الجديدة

> **الحركة مسموحة فقط حين تخدم الفهم: ملاحظات فورية (toast/تأكيد)، انتقال حالة، إرشاد التركيز. كل ما عداها → ساكن.**

| النمط الحالي | القرار | البديل |
|--------------|--------|--------|
| تلاشي/انزلاق كل صفحة عند التنقّل (`Layout.tsx`) | **يُزال أو يُختصر** لـ150ms opacity فقط | انتقال فوري أو تلاشي خفيف جدًّا |
| كشف `whileInView` لكل بطاقة/قسم عند التمرير | **يُقلَّص** إلى الأقسام البطلة (hero) فقط، بلا stagger متسلسل طويل | ظهور فوري للمحتوى أسفل الطيّة |
| `stagger` متتالٍ على شبكات البطاقات | **يُلغى** (يؤخّر رؤية المحتوى ويُشتِّت) | الشبكة تظهر دفعة واحدة |
| هالات `blur-3xl` + تدرّجات + توهّج زخرفي | **يُخفَّف** بشدة: خلفية هادئة، عنصر زخرفي واحد كحدّ أقصى للقسم | مساحات بيضاء بدل الزخرفة |
| حركات hover قوية (`scale 1.03`, `y:-8`) | **تُهدَّأ** إلى `scale 1.01` أو تغيّر ظلّ خفيف | تغذية راجعة دقيقة لا قافزة |

### 2.2 مكسب فوري (سطر واحد) — يُطبَّق أولًا

تغليف التطبيق بـ`<MotionConfig reducedMotion="user">` في `main.tsx` يجعل `framer-motion` يحترم إعداد «تقليل الحركة» في نظام المستخدم **عالميًّا** (يعالج 311 ملفًّا دفعة واحدة دون لمسها). آمن تمامًا: لا يغيّر تجربة من لم يُفعّل الإعداد.

```tsx
// main.tsx
import { MotionConfig } from 'framer-motion'
// ...
<MotionConfig reducedMotion="user">
  <App />
</MotionConfig>
```

### 2.3 خفض شدّة الحركة الافتراضية (قرار تصميم)

ما سبق يحترم تفضيل النظام؛ لكن لتهدئة التجربة **للجميع** نُنشئ ثوابت حركة موحّدة ونستبدل القيم المبعثرة بها:

```ts
// src/lib/motion.ts  (مصدر واحد للحقيقة)
export const fadeQuiet = { initial: { opacity: 0 }, animate: { opacity: 1 }, transition: { duration: 0.15 } }
export const hoverSubtle = { whileHover: { scale: 1.01 } }
// لا stagger افتراضي، لا انزلاقات طويلة، لا whileInView على الشبكات
```

## 3. تبسيط التدفّقات وتقليل الخطوات (علاج «خطوات كثيرة») 🪜

### 3.1 المنهجية لكل تدفّق

لكل تدفّق متعدّد الخطوات نطبّق هذا المرشّح بالترتيب:

1. **احذف**: هل هذه الخطوة/الحقل ضروريّ فعلًا للإنجاز؟ إن لا → احذفه.
2. **ادمج**: هل يمكن جمع خطوتين في شاشة واحدة منطقية؟
3. **أجّل**: هل يمكن نقل المتقدّم إلى ما بعد الإنجاز («أكمِل ملفك لاحقًا»)؟
4. **افترض**: هل يمكن قيمة افتراضية ذكية بدل سؤال (البلد من الهاتف، اللغة من المتصفّح)؟
5. **أظهِر التقدّم**: إن بقيت خطوات، أظهِر مؤشّر «خطوة س من ص» واضحًا.

### 3.2 التدفّقات المستهدَفة (بالأولوية)

| التدفّق | الملف | المشكلة المتوقّعة | التبسيط المقترَح |
|---------|-------|-------------------|------------------|
| **التسجيل في دورة** | `Register.tsx` (~19KB) | حقول كثيرة دفعة واحدة + اختيار مزوّد دفع | شاشة واحدة قصيرة: الأساسي فقط (اسم/هاتف/بريد)؛ الدفع خطوة منفصلة بعد التأكيد؛ قيم افتراضية ذكية |
| **معالج النماذج** | `emc-form-wizard` (~17KB) | خطوات متعدّدة قد تكون قابلة للدمج | مراجعة الخطوات: دمج المترابطة، مؤشّر تقدّم، حفظ تلقائي للمسوّدة |
| **طلب ورشة** | `SubmitWorkshop` (~49KB — الأضخم) | ملف ضخم = نموذج مرهِق غالبًا | تقسيم لأقسام قابلة للطيّ + كشف تدريجي + إخفاء الحقول المتقدّمة |
| **التطوّع** | `VolunteerApply.tsx` (~19KB) | نموذج طويل | الأساسي أولًا، والتفاصيل بعد القبول المبدئي |
| **التواصل** | `Contact.tsx` (~19KB) | قد يكون مثقلًا لصفحة تواصل | تقليصه لأبسط نموذج ممكن (اسم/بريد/رسالة) |

> **ملاحظة:** الأرقام تقديرية من حجم الملفّات؛ الخطوة الأولى في التنفيذ هي **تدقيق ميداني** لكل تدفّق (عدّ الخطوات/الحقول الفعليّة) قبل القصّ — موثّق في الـ backlog.

### 3.3 تقليل احتكاك الإدخال

- **توحيد النوافذ** على نمط `<dialog>`/`showModal()` من `ConfirmDialog` (حصر تركيز + Escape + استعادة تركيز) — المستخدم لا «يتعثّر» خارج النافذة. [تقرير 07 / A11Y-1]
- **ملتقطات تاريخ تعمل بلوحة المفاتيح** + قيود `min`/`max`/`disabledDate` تمنع الأخطاء قبل وقوعها. [A11Y-2, §4.6]
- **تحقّق فوري على العميل** (لا انتظار الخادم لاكتشاف خطأ حقل) — رسائل واضحة بجانب الحقل.

## 4. تبسيط الواجهة ونظام التصميم (علاج «معقّدة») 🧩

### 4.1 توحيد المكوّنات (مصدر واحد لكل غرض)

| الغرض | الحالي (فوضى) | الهدف |
|-------|----------------|-------|
| زرّ | `AppButton` + `EmcButton` | **`EmcButton` فقط**؛ `AppButton` → re-export رفيع ثمّ يُهلَك |
| عنوان قسم | 4 ملفّات | **`SectionHeading` واحد** |
| بطاقة إحصاء | `StatCard` + `StatTile` | **`StatTile` واحد** |
| دمج الأصناف | `.join(' ')` في 7 ملفّات | **`cn()` في كل مكان** |

### 4.2 لون واحد للـaccent، وتباين سليم

- حذف اللون البُنّيّ الدخيل `#b9872f` نهائيًّا — الـaccent الوحيد هو برتقالي العلامة.
- إدخال token برتقالي **أغمق** (~`#B5650F`) للنصّ والروابط لتجاوز عتبة WCAG AA (الحالي ~2.3:1)، وقصر `#EC943C` على المساحات الكبيرة/غير النصّية. [A11Y-3]
- إزالة الـ**75 لون hex خام** من `components/ui` واستبدالها بأصناف الـtokens، مع قاعدة lint تمنع تكرارها.

### 4.3 تهدئة الكثافة البصرية

- **ظلّ واحد** لكل بطاقة (لا ظلّ + حلقة + حدّ معًا) — اختَر `shadow-emc-sm` أو حلقة، لا كلاهما.
- **هرميّة نصّية أوضح**: عنوان بارز واحد لكل شاشة، وأحجام نصّ أقلّ تنوّعًا.
- **مساحة بيضاء أكثر**: التنفّس البصري يقلّل الإحساس بالتعقيد دون حذف محتوى.
- **شارات أقلّ**: لا تكدّس 3-4 شارات على بطاقة؛ أبقِ الأهمّ.

### 4.4 تبسيط التنقّل

- مراجعة الشريط الجانبي للوحة التحكّم (`DashboardLayout` ~32KB، أدوار متعدّدة): تجميع منطقي، طيّ المجموعات غير النشطة، وإبراز المسار الحالي بوضوح.
- شريط علوي عام (`Navbar`) أبسط: روابط أساسية ظاهرة، والبقية في «المزيد».

## 6. مقاييس النجاح (كيف نعرف أننا نجحنا؟)

| المقياس | الحالي (تقديري) | الهدف |
|---------|------------------|-------|
| ملفّات تحترم `prefers-reduced-motion` | 2 | 100% (عبر `MotionConfig`) |
| خطوات تدفّق التسجيل | يُحدَّد بالتدقيق | **−40%** على الأقلّ |
| مكوّنات لنفس الغرض (زرّ/عنوان) | 2–4 | 1 |
| ألوان hex خام في `ui/` | 75 | 0 |
| مواضع تخالف تباين AA | 187 | 0 |
| نوافذ بحصر تركيز | 1 من ~9 | كلّها |
| زمن أوّل رسم للنصّ (FCP) | يحجبه `@import` الخطوط | تحسّن ملموس |

> **القاعدة الذهبية للقياس:** «هل يستطيع مستخدم جديد إكمال التسجيل دون تردّد أو سؤال؟» — إن نعم، نجحنا.

## 7. ما الذي لا نفعله (حدود الخطة)

- ❌ لا نحذف ميزات وظيفية — التبسيط بصريّ وتدفّقيّ، لا وظيفيّ.
- ❌ لا نعيد بناء نظام التصميم من الصفر — نُكمل الهجرة الموجودة (Emc*) لا نبدأ جديدة.
- ❌ لا نُجمّل قبل أن نُصلح — إصلاح التباين والوصول جزء من «الجمال»، لا زينة لاحقة.
